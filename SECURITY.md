# Security

## Reporting a vulnerability

Please report security issues privately through GitHub's
[private vulnerability reporting](https://github.com/marcdomain/vaqum/security/advisories/new)
rather than a public issue. Include the vaqum version (`vaqum --version`),
your OS, and a sample archive or the steps that trigger the problem.

## Encryption

`vaqum compress -e` (password) and `--key-file` (key file) encrypt the
compressed data:

| Part | Choice |
| --- | --- |
| Cipher | ChaCha20-Poly1305 (authenticated encryption), in the STREAM construction with 64 KiB chunks |
| Key derivation | Argon2id with 64 MiB of memory, 3 passes, a random 16-byte salt per archive |
| Nonces | A random 7-byte prefix per archive plus a chunk counter, so no nonce is ever reused under the same key |
| Stored in the archive | Only the salt and nonce prefix. The password and key are never stored |

Any change to the encrypted data, including truncation, makes decryption
fail, and vaqum writes nothing out.

Archives encrypted by vaqum 1.2.5 and earlier used Argon2id's default
settings (19 MiB, 2 passes). They still open, and a header flag records
which settings an archive uses. Re-compress old archives to give them the
stronger settings.

### Encrypting for people (`--to`)

Archives encrypted for recipients follow age's X25519 recipient design
(age-encryption.org/v1), built from the same audited primitives:

| Part | Choice |
| --- | --- |
| Keys | X25519 (curve25519-dalek) for encryption, Ed25519 (minisign) for signing, generated by `vaqum keygen` |
| Per archive | A random 32-byte file key; the payload key is derived from it with HKDF-SHA256 |
| Per recipient | An ephemeral X25519 exchange; HKDF-SHA256 derives a wrap key that seals the file key with ChaCha20-Poly1305 |
| Header | HMAC-SHA256 (keyed from the file key) over every header byte, so names, sizes and the recipient list can't be altered |

The identity file holds your secret keys. By default `vaqum keygen` seals
them with a passphrase: ChaCha20-Poly1305 under an Argon2id key (64 MiB,
3 passes, random salt), with the public key bound in as associated data,
so a swapped public key or any edit is detected. The file is readable only
by you (mode 600). Keys made with `--no-passphrase` (for CI) are stored
unsealed, like an unprotected SSH key. Public keys (`vqm1…`) carry a
checksum, so a mistyped key is refused rather than silently encrypting to
the wrong key.

### Signatures

`vaqum sign` and `compress --sign` write a standard minisign signature
(Ed25519 over a BLAKE2b hash of the file) to `<archive>.minisig`.
`vaqum verify --from` and `decompress --from` check it against the sender's
public key; `decompress --from` extracts nothing unless it matches.

### Limits

- The archive header is readable without the key. Anyone holding the file
  can see the original file name, its size, its SHA-256 checksum, that it is
  encrypted, and (for `--to` archives) how many recipients it has. They
  can't see the contents. For `--to` archives the header is also
  authenticated, so any change to it is detected. For password archives a
  changed header can't reveal or alter the contents either: decryption fails
  or the checksum no longer matches.
- Encryption is only as strong as the password. vaqum warns about weak
  passwords; a long random key file (`--key-file`) avoids the problem.

## App secrets (`vaqum secrets`, `vaqum run`)

A secrets file (`.env.vqm`) keeps names and members readable and values
encrypted:

| Part | Choice |
| --- | --- |
| Access | A random 32-byte file key, wrapped for each member exactly like `--to` archives |
| Values | ChaCha20-Poly1305 under a key derived from the file key, a random nonce per value, and the secret's name as associated data (a value can't be moved to another name) |
| Integrity | HMAC-SHA256 keyed from the file key over the marker, members, wrapped keys and every entry in order |

What that guarantees: someone without a member's key (and its passphrase)
can't read any value, and can't change, move, rename, add or remove
anything, or add themselves as a member, without the file being refused.
Removing a member re-encrypts everything under a new file key.

What it can't guarantee:
- A removed member may already have the values (and git history keeps
  older versions of the file), so rotate the secrets they could read.
- Members can edit the file; signatures (`vaqum sign`) record who did.
- `vaqum run` gives the secrets to the command you start, as environment
  variables; that program (and anything that can inspect its environment,
  such as the same user or an administrator) can read them.
- Malware running as you can capture your passphrase as you type it.

## Leak check

`compress` warns when what you're packing looks like it holds credentials:
`.env` files, SSH and PEM keys, keystores, cloud credential files, and
tokens for AWS, GitHub, GitLab, Slack, Stripe, OpenAI, Anthropic, Google,
npm, PyPI, SendGrid and Twilio. It reports the file and the kind of secret,
never the value. It knows common formats, not every secret, so it's a
safety net rather than a guarantee.

## Opening untrusted archives

vaqum is built to open archives from people you don't trust:

- **No writing outside the output directory.** Stored names and paths with
  `..`, absolute paths, or paths that would go through a symlink are refused,
  for `.vqm`, zip and tar.gz alike.
- **Decompression bombs are stopped.** Archives that claim an implausible
  expansion ratio, or more data than fits on disk, are refused up front.
  Decompression also stops the moment the data grows past the size the
  archive declared, so a lying header can't get around those checks.
- **No partial files.** Output is written to a randomly named temp file and
  moved into place only once complete (and verified, with `--verify`).
  Temp files are created exclusively, so a file or symlink planted in a
  shared directory can't redirect the write.
- **Risky contents are flagged.** `list` and `decompress` warn about
  programs disguised as documents, names that use invisible characters to
  fake their extension, files that run code when opened, setuid bits, links
  pointing outside the archive, and nested archives. This isn't a virus
  scanner: scan untrusted programs with your antivirus before running them.
- **The "downloaded from the internet" mark is kept.** Files extracted from
  a downloaded archive keep its macOS quarantine flag or Windows Mark of the
  Web, so Gatekeeper and SmartScreen still check programs before they run.

## Browser viewer

The viewer at marcdomain.github.io/vaqum (source in `web/`) opens archives
entirely in the visitor's browser:

- Nothing is uploaded. The page's Content-Security-Policy allows no
  external scripts and no connections except loading its own files.
- It uses vaqum's own header parser and risk checks, verifies every
  archive's SHA-256 checksum, and caps decompressed output against the size
  the header declares (and 1.5 GB overall).
- Names from the archive are only ever shown as text, never as HTML, so a
  crafted archive can't inject code into the page.
- Its dependencies are audited in CI alongside the CLI's.

## `shred` limits

`shred` overwrites a file's contents before deleting it. That is
best-effort, not forensic-grade:

- SSDs and flash drives move data around internally (wear-leveling, TRIM).
- Copy-on-write filesystems (APFS, the macOS default; btrfs; ZFS) write
  changes to new blocks and leave the old ones in place.
- Backups, snapshots (for example Time Machine) and cloud sync keep their own
  copies.

Full-disk encryption (FileVault, BitLocker, LUKS) is the reliable protection.
`shred` refuses to follow symlinks, so it can't be tricked into destroying a
file somewhere else.

## Verifying downloads

Every release binary comes with a SHA-256 checksum, which the npm package,
`install.sh` and `install.ps1` all verify before installing. Release
binaries also carry signed build provenance, which proves a file was built
by this repository's release workflow:

```sh
gh attestation verify vaqum-1.3.0-x86_64-unknown-linux-musl.tar.gz --repo marcdomain/vaqum
```

## Testing and supply chain

- Every hostile-archive case above has a test that builds the malicious
  archive and checks vaqum refuses it.
- The archive readers are fuzzed: millions of malformed inputs, weekly in CI
  (`.github/workflows/fuzz.yml`), checking for crashes and for any write
  outside the output folder.
- Dependencies are checked against the RustSec advisory database on every
  push and weekly (`cargo audit`); Dependabot proposes updates.
- GitHub Actions and build tools in CI are pinned to exact commits.
- The npm package has no dependencies.
